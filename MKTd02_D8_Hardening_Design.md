# MKTd02 — D8 Hardening DESIGN (propose-only)

**Target:** open-chatZD @ `7b5ac7ccb` + current P1 tree · **Engine:** mktd02-v0.4.1
**Mode:** inspect-only — no code, no tests. Output is a design for G + Claude review.
**Locked (not re-litigated):** central `mutate_state` write-guard; Phase-A precondition (not the guard) solves financial stranding; precondition checked *before* lock/tombstone; existing entry + post-await `assert_not_pending_deletion` stay as defense-in-depth.

All file:line references are to the current tree.

## Problem restatement (the two confirmed bypass classes)

`assert_not_pending_deletion` (`lib.rs:770`) is enforced only at the two funnels:
- `execute_update` — entry check `lib.rs:781`.
- `execute_update_async` — entry check `lib.rs:790`, **and** a post-await re-check `lib.rs:794`.

But `mutate_state` (generated by the shared macro `canister_state_macros/src/lib.rs:36`) is callable directly, and **72 of 74** user-canister call-sites do not pass through those funnels (see D7). Two exploitable classes:

1. **Timer / job PII writers run outside the funnels.** E.g. `HardDeleteMessageContentJob` (`timer_job_types.rs:147`), `MessageReminderJob` (`timer_job_types.rs:201`), the deferred stable-memory GC (`jobs/garbage_collect_stable_memory.rs:24`) — none gated.
2. **Async value-bearing commit before an `await`.** A handler whose entry check passed mutates value state, then `await`s; the commit lands at the await boundary; a concurrent Phase A tombstones during the await. The post-await re-check (`lib.rs:794`) *traps the resumed message and rolls it back* — but only for state the handler had not already externalized (e.g. a ledger transfer already dispatched). The strand is the **financial** residue, which is why D3/D4 (precondition), not the guard, must own it.

## D1 — Central guard mechanism

**Recommendation: a guarded `mutate_state` + a sibling `mutate_state_bypass`, with the guard as a single heap-`bool` check. No flag, no token.**

Mechanism (one shared-macro change, `canister_state_macros/src/lib.rs:36-41`):
- The generated `mutate_state` calls an optional `WriteGuard` hook on `$type` *before* `f`. The trait has a **default no-op** impl, so every other canister (group, community, user_index, …) compiles to exactly today's code — zero hot-path cost.
- The macro additionally emits `mutate_state_bypass` that performs the same borrow **without** the hook. Only the privileged paths in D2 call it.
- The user `RuntimeState` overrides the hook as the entire guard body:
  `if self.data.pii_tombstoned { ic_cdk::trap("…D8…") }` — reading the existing heap bool `Data::pii_tombstoned` (`lib.rs:505`).

**Cheap-check guarantee:** one branch on a `bool` already resident in `Data` — **no extra stable-memory reads, no allocation, no clone** on the write path. For non-user canisters the default hook inlines to nothing.

**Why not the alternatives:**
- **(b) reentrancy flag held for the privileged op's duration.** A *thread-local* flag is **trap-unsafe**: IC `ic0.trap` aborts the message without unwinding the Rust stack, so an RAII `Drop` that clears the flag **does not run** — a trap mid-bypass leaves the flag stuck `true`, opening the guard for the *next* message. A *state-resident* flag (on `Data`) is trap-safe (rolled back on trap) but introduces a chicken-and-egg: the guard reads it at `mutate_state` entry, yet only a write can set it. Both are strictly more complex than "which function did you call," for no added safety.
- **(c) typed write-token.** Compile-time proof of authorization, but must be threaded through all 72 call-sites and every helper signature — invasive and churny for a property the bypass set already pins.

The sibling approach makes the **bypass set itself the auditable security boundary** (D2), which is the intended review surface.

## D2 — Exact bypass set (the security boundary: exhaustive + minimal)

A site needs `mutate_state_bypass` **iff** it must write while `pii_tombstoned == true` (or across the upgrade of a tombstoned canister).

| # | Site | file:line | Why it must bypass |
|---|------|-----------|--------------------|
| 1 | `MKTdUserAdapter::tombstone_state` | `mktd.rs:266` (closure 266–315) | Phase-A erase + sets `pii_tombstoned=true` (`mktd.rs:314`). *Today* its single `mutate_state` checks the flag at entry while it is still `false`, so it would pass even unguarded — but it MUST be `bypass` defensively so any future second write (or engine re-entrancy) cannot self-trap. |
| 2 | deferred stable-memory GC job | `jobs/garbage_collect_stable_memory.rs:24` | Runs **after** tombstone (it drains `stable_memory_keys_to_garbage_collect`, `lib.rs:495`, enqueued by `tombstone_state` via `delete_direct_chat`). `pii_tombstoned` is `true` here → guard would trap → **the deferred PII purge never completes (PII strand)**. This is the critical bypass. |
| 3 | lifecycle `init` | `lifecycle/init.rs:36` | Bypass (or guard-inert pre-first-message). At install `pii_tombstoned==false` so it passes today, but listing it makes the contract explicit. |
| — | lifecycle `post_upgrade` | `lifecycle/post_upgrade.rs:14-41` | **Not a bypass site (verified).** It hydrates via `init_state` (`:26`) and reconnects the engine via `with_memory_manager` (`:35`) — it never calls host `mutate_state`. A tombstoned-but-finalized canister upgrades cleanly; a *pending-finalization* canister traps by design in `mktd02::on_post_upgrade` (`:30-32` comment). No guard interaction. |

**Explicitly NOT in the bypass set (and why):**
- **Phase C finalize** (`updates/mktd_finalize_deletion.rs:22`) writes **engine stable storage** via `mktd02::finalize_receipt_after_host_authorization` — it never touches host `mutate_state`/`Data`. It is *outside the host write-guard's scope entirely*; no bypass needed.
- **Recovery / admin finalize** — **does not exist in the P1 tree** (`updates/mod.rs` exposes only `mktd_execute_deletion`, `mktd_finalize_deletion`). When P3 adds a recovery/admin finalize that writes host state, it **must** join this set; flag for the P3 packet.
- `run_regular_jobs`/`flush_pending_events` (`lib.rs:800,804`) — *not* privileged. Post-tombstone they should be unreachable: new updates are blocked at the funnels, and the timer path that calls `run_regular_jobs` (`timer_job_types.rs:120`) is removed by D6's drain. If one fires, trapping is the correct (harmless) outcome.

Minimal set today = **{1 tombstone, 2 deferred-GC}**, plus init (#3) for explicitness. `post_upgrade` verified out.

## D3 — Phase-A quiescence predicate (value-bearing in-flight / locked state)

"In flight / locked" = an operation that has **moved or committed value and has an outstanding settlement leg** (a transfer dispatched, tokens parked in escrow, a payment lock held). Completed/historical records are *not* in flight.

| Value state | field (file:line) | "in flight" predicate | source of the leg |
|---|---|---|---|
| Token swap incomplete | `Data::token_swaps` `lib.rs:477`; `TokenSwap::success` `model/token_swaps.rs:54` | any swap with `success.is_none()` | multi-leg DEX flow, retried by `ProcessTokenSwapJob` (`updates/swap_tokens.rs:280`) |
| Token-swap retry queued | `Data::timer_jobs` `lib.rs:471` | any `TimerJob::ProcessTokenSwap` (`timer_job_types.rs:19`) | equivalent to the above |
| Streak-insurance payment lock | `Streak::payment_lock` `model/streak.rs:22` (`#[serde(skip)]`) | `payment_lock == true` | acquired `pay_for_streak_insurance.rs:89`, released `:43` around an `await` |
| P2P-swap escrow deposit pending | `Data::timer_jobs` `lib.rs:471` | any `TimerJob::NotifyEscrowCanisterOfDeposit` (`timer_job_types.rs:20`) | tokens deposited to escrow, escrow not yet notified |
| P2P-swap cancel pending | `Data::timer_jobs` | any `TimerJob::CancelP2PSwapInEscrowCanister` (`timer_job_types.rs:21`) | reclaim of escrowed tokens in flight |
| P2P-swap accept reserved | chat events reservation | a reserved-but-uncommitted accept (`reserve_p2p_swap` `accept_p2p_swap.rs:126`, released `:102`) | tokens mid-accept |
| Open P2P-swap with escrowed funds | `Data::p2p_swaps` `lib.rs:478`; `model/p2p_swaps.rs:21` | any swap this user created, still open/unexpired, token0 in escrow | **see D5 FLAG** |
| Msg-with-transfer post-transfer, pre-send | `Data::timer_jobs` | any `TimerJob::SendMessageToGroup`/`SendMessageToChannel` (`timer_job_types.rs:23,24`) | transfer done, group/channel delivery retrying (`updates/send_message_with_transfer.rs:120,228`) |

**Consolidated predicate** (`is_quiescent_for_deletion(state) -> bool`), all must hold:
1. `token_swaps` has no entry with `success.is_none()`;
2. `streak.payment_lock == false`;
3. `timer_jobs` contains none of: `ProcessTokenSwap`, `NotifyEscrowCanisterOfDeposit`, `CancelP2PSwapInEscrowCanister`, `SendMessageToGroup`, `SendMessageToChannel`;
4. no reserved/uncommitted p2p accept;
5. no open self-created p2p swap with funds still in escrow (D5).

**Out of D3 scope (not strands):** `pin_number` attempt back-off (`model/pin_number.rs:10`, temporal lock, no value); `MarkVideoCallEnded`, `MarkP2PSwapExpired`, `MessageReminder`, `RemoveExpiredEvents`, `HardDeleteMessageContent`, `DeleteFileReferences`, `ClaimOrResetStreakInsurance` (no outstanding *outbound* value — insurance was pre-paid). These are drained by D6, not blocked by D3.

## D4 — Precondition placement + semantics

**Placement (G's tightening):** the very first statement of `mktd_execute_deletion` (`updates/mktd_execute_deletion.rs:17`), **before** `record_id` derivation, **before** any engine call, **before** the finalization lock is acquired and **before** `tombstone_state` runs:

```
read_state(is_quiescent_for_deletion)  →  if false: return Error("…settle or cancel in-flight value operations first…")
```

**Rejection semantics:** a pure `read_state` check that returns `Response::Error(String)` with **zero state change** — no lock acquired, no tombstone, no timer touched, no `pii_tombstoned` set. The canister remains in the **no-pending-deletion** state, fully operational. Because nothing has been written, **rejection leaves zero residue** by construction (the only writes in Phase A happen strictly after this gate).

**User-facing semantics (P1):** *reject and let the user resolve.* The error tells the owner to **settle or cancel** outstanding value operations (wait for swaps to complete, let escrow deposits/cancels drain, finish the streak-insurance payment, await message-with-transfer delivery) and retry deletion. **No auto-cancel / auto-refund in P1** — automated unwinding is P3.

This is strictly stronger than gating at lock-acquisition: a rejected deletion can never leave a half-armed pending state.

## D5 — G-3 ERASE-scope consistency (cross-check tombstone erase vs D3)

`tombstone_state` (`mktd.rs:265-315`) erases, among scalar PII, these **value-bearing** fields. Each must be empty/settled at Phase A — i.e. covered by D3 — or it is a residual strand:

| Erased value field (mktd.rs) | Covered by D3? | Verdict |
|---|---|---|
| `token_swaps` `:307` | yes (pred 1/3) | ✓ only completed history remains to erase |
| `p2p_swaps` `:308` | **partially** | **FLAG — see below** |
| `streak` `:297` (incl. insurance) | payment leg via pred 2 | ✓ payment lock covers the only outbound leg |
| `saved_crypto_accounts` `:304`, `btc_address` `:305`, `one_sec_address` `:306` | n/a (address book / deposit addresses) | DISCLOSE-class: external in-flight deposits are not locally observable — not a P1 *local* strand, but **note to G** |
| `diamond_membership_expires_at` `:309`, `premium_items` `:310` | consumed/pre-paid benefits | not a strand (no reclaimable outbound value); erasing forfeits remaining benefit — DISCLOSE/UX note |

**G-3 RESOLUTION / FLAG:** `p2p_swaps` erase (`mktd.rs:308`) is the one genuine strand risk. An **open** swap this user created has `token0` parked in the **escrow** canister until accept/cancel/expire. Recommend G ratify clause 5 as load-bearing for G-3.

All other erased value fields are covered (settled before erase) by D3 clauses 1–4 or are consumed-benefit / external-deposit DISCLOSE items outside P1 local-strand scope.

## D6 — Timer-queue handling

**Recommendation: Phase A drains the `timer_jobs` queue (`cancel_jobs(|_| true)`, `lib.rs:471` queue) inside `tombstone_state`'s bypass write; the separate deferred-GC timer is left running (and is bypassed).**

Rationale:
- Post-tombstone, any guarded `TimerJob` that fires hits `run_regular_jobs` (`timer_job_types.rs:120`) → `mutate_state` → **trap**, then the timer framework re-enqueues → **trap-retry churn and wasted cycles**. Draining the queue removes the source.
- It is **safe to drain at this point**: D3 guarantees no *value-bearing* job is present (`ProcessTokenSwap`/`Notify…`/`Cancel…`/`SendMessageTo…` all block deletion). What remains is purely local bookkeeping (`MessageReminder`, `RemoveExpiredEvents`, `MarkVideoCallEnded`, `HardDeleteMessageContent`, `DeleteFileReferences`, `ClaimOrResetStreakInsurance`) whose continuation is moot for a deleting account.
- `cancel_jobs` already cancels the underlying `ic_cdk` timers (`canister_timer_jobs/src/lib.rs:50`), so no orphaned callbacks remain.
- **The deferred stable-memory GC is a *separate* timer** (`garbage_collect_stable_memory.rs:13`, not in `timer_jobs`); draining `timer_jobs` does not touch it, and it continues via the D2 #2 bypass to finish the PII purge.

Preferred over a per-`TimerJob::execute` "skip if tombstoned" guard: draining is one action with no recurring churn, vs. a skip that still wakes, borrows, and re-evaluates on every scheduled tick.

## D7 — Blast radius + completeness

- **Total `mutate_state` call-sites (user impl): 74.** Breakdown: 3 inside the `execute_update` funnel (`lib.rs:780,800,804`), 12 timer/job (`timer_job_types.rs` ×11 + GC ×1), 1 lifecycle (`init.rs:36`; post_upgrade TBV), 1 MKTd tombstone (`mktd.rs:266`), 57 async `_impl` handlers.
- **Under guard: all 74** route through the guarded `mutate_state` and are blocked when tombstoned. **Bypass: 2** privileged (D2 #1 tombstone, #2 deferred-GC) + init (#3) for explicitness — i.e. **~4 % of sites are privileged**, the rest are uniformly gated by one mechanism.
- **Completeness confidence: high.** The guard is *complete by construction* — it sits on the single chokepoint every write must cross (`canister_state_macros:36`); there is no second way to obtain `&mut RuntimeState`. Correctness then reduces to the bypass set being right, which is small, enumerated, and audit-reviewable (D2). The async-commit residue the guard cannot catch (value already externalized) is owned by D3/D4, not the guard.
- **Hot path stays cheap:** one `bool` branch on already-resident `Data::pii_tombstoned`; non-user canisters pay nothing (default no-op hook).

**Open verification items for the implementation packet:** (i) `post_upgrade` — **resolved**: no host `mutate_state`, no bypass (`post_upgrade.rs:26,35`); (ii) when P3 adds a recovery/admin finalize that writes host state, it must join the D2 bypass set.
